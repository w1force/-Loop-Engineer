# CCB observability evidence

The service under test is `/Users/wangzheng.440/claude-code` (CCB). Use its existing
OpenTelemetry implementation; do not scrape a Trace ID from human-readable logs when
OTLP evidence is available.

## Local export

Generate a coordinator-only token and run the Loop Engineer receiver. CCB's beta
exporter does not pass custom authorization headers, so its OTLP endpoints remain
unauthenticated but loopback-only; execution-window writes and query APIs require
the token.

```bash
export LOOP_ENGINEER_COORDINATOR_TOKEN='<at-least-32-random-characters>'
uv run python -m core.observability \
  --database .loop-engineer/observability.sqlite3 \
  serve --ccb-debug-dir /Users/wangzheng.440/.claude/debug
```

Run a CCB verification process with detailed OTLP export enabled:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export ENABLE_BETA_TRACING_DETAILED=1
export BETA_TRACING_ENDPOINT=http://127.0.0.1:4318
export OTEL_RESOURCE_ATTRIBUTES='service.name=claude-code,service.version=<git-sha>,verification.run_id=<run>,verification.scenario_id=<scenario>,verification.variant=<control-or-candidate>,verification.input_digest=<sha256>'
# Start CCB with --debug so its default file remains ~/.claude/debug/<session-id>.txt.
```

Use a separate process/container and resource attributes for each control/candidate
scenario. Record the normalized scenario input before launch. A trusted component
must call SDK forceFlush for traces and logs and submit the bound flush barrier with
the coordinator credential; after CCB exits, the launcher records one execution
window directly through `LocalObservabilityStore.record_execution()`. The repair or
candidate process must not hold this credential or declare its own barrier/window
complete. The current Docker path does not yet provide this trusted CCB
forceFlush/network adapter, so this remains an integration requirement rather than
proven E2E behavior.
Do not point `CLAUDE_CODE_DEBUG_LOGS_DIR` at a directory in this CCB checkout:
despite its name, the implementation treats that value as the complete log file
path. Keeping the default per-session filename preserves `session.id` correlation.

## Field sources

| Verification field | CCB/local source |
|---|---|
| `trace_id`, `span_id` | Generated by the CCB OpenTelemetry SDK and received in OTLP envelopes |
| `session_id` | CCB `session.id` span attribute; also the debug filename stem |
| scenario pairing | Injected trusted `OTEL_RESOURCE_ATTRIBUTES` values |
| requested model | `model` on `claude_code.llm_request` spans |
| actual response model | `model` on the CCB `api_request` OTLP log event |
| max input tokens | Per request `input_tokens + cache_read_tokens + cache_creation_tokens`, then scenario maximum |
| ERROR observations | Span ERROR status, exception events, non-empty error attribute, or `success=false` |
| fallback | Only an explicit fallback field/event; multiple model names are not proof |
| finished | Trusted launcher process terminal state or a future CCB `agent.finished` attribute |
| log fingerprint | Severity, parsed error type, normalized message, event code and business frame |

## Current CCB gaps

CCB does not currently put all article fields on one query-level Trace contract:

- `trace_id` exists in OpenTelemetry, but the Langfuse debug message prints the
  observation/span ID rather than exposing a durable verification mapping API;
- the interaction root does not explicitly record the actual response model or
  `agent.finished`;
- fallback is emitted as a separate analytics event, not a guaranteed Trace
  attribute tied to the scenario;
- API `requestId` is present in API analytics/debug paths but not guaranteed on the
  interaction/LLM Span;
- `verification.run_id`, scenario, variant and input digest are not native CCB
  fields and must be injected by the trusted launcher;
- CCB debug logs are text lines and normally correlate through `session.id`, not a
  native log-record Trace ID;
- derived OTel ERROR counts are not byte-for-byte identical to Langfuse's
  observation-level `level=ERROR` count.

CCB emits `tool_result success=false` as an OTLP event without a guaranteed ERROR
severity. The local receiver promotes that explicit failure signal to ERROR and
fingerprints its `error` attribute. CCB OTLP logs are not guaranteed to carry the
active Trace context, so the repository discovers Trace IDs from spans by the
trusted run/scenario/variant/input window; a CronJob does not pass a Trace ID to the
diagnosis service.

The providers fail closed when a mandatory metric cannot be established. Do not turn
absence of a field into `false`, zero, or finished=true.
